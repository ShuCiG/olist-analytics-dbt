Short ADR-style entries. Newest last. Format: context → decision → why.

## D1 · 2026-10-10 · Dataset: Olist Brazilian e-commerce (Kaggle)

DuckDB = zero infra, fast local loop. BigQuery adds a real cloud DWH and enables true CD. Two targets force cross-DB SQL.

dlt loads every column as string; dbt staging casts types. Why: zip prefixes have leading zeros, raw mirrors source exactly, casting logic is visible and tested in dbt.

## D9 · 2026-10-10 · dbt conventions
- dbt runs from `transform/`; `profiles.yml` committed (no secrets; DuckDB path via `DBT_DUCKDB_PATH`).
- Custom `generate_schema_name`: dev/prod → plain schema (`staging`, `marts`); other targets (CI) → `<target_schema>_<schema>` for isolation.
- Test syntax uses `arguments:` block (dbt ≥1.10 style).
- Known data defects get `severity: warn` instead of being hidden — documents data quality.
- dim_customers grain = `customer_unique_id` (person), not order-level `customer_id`.

## D10 · 2026-10-10 · Mart modeling choices
- `order_amount` (items + freight) and `payment_value` (actually paid) kept separate; mismatch >1 BRL is a warn test, not "fixed".
- Latest review per order wins (`int_order_reviews_deduplicated`).
- Geolocation collapsed to zip centroid (avg lat/lng); dims left-join it (278 customer zips unmatched).
- Missing category → English translation → Portuguese name → 'unknown'.
- `dim_date` via `dbt_date.get_date_dimension` (2016–2019).

## D12 · 2026-10-10 · SQL linting
- sqlfluff with **dbt templater** (renders real macros), dialect duckdb, max line 120.
- Templater uses a dedicated `lint` target (DuckDB `:memory:`): no data or DB file needed, works in CI and from repo root.
- ST06 (column order by expression type) excluded: marts group columns by business meaning.
- Jinja loop bodies indented one level; avoid whitespace control (`-%}`) inside select lists, it confuses LT02.
- CI: `sqlfluff lint` job gates `dbt build` (`needs:`). Both are required checks (a skipped required job would otherwise count as passing).
- pre-commit: standard hygiene hooks + `no-commit-to-branch main` + local sqlfluff hook via `uv run` (same version as CI).

## D13 · 2026-10-11 · Unit tests
- Native dbt `unit_tests:` (≥1.8), in `_<layer>__unit_tests.yml` next to model ymls.
- Unit-test business rules, not SQL: only models with real logic (pivot, lateness, LTV/location). Staging renames are covered by data tests.
- Fixtures list only columns the model reads; `expect` lists only asserted columns.
- Fixture timestamps avoid midnight-crossing intervals: `dbt.datediff` counts boundaries on DuckDB, BigQuery semantics may differ.
- New tests are mutation-checked once (break the rule, confirm failure).
- Unit tests run inside `dbt build` (before the model is built; parents must exist). Prod runs (phase 3) will add `--exclude-resource-type unit_test`.

## D14 · 2026-10-11 · Contracts, money type, generic test, doc blocks
- Enforced contracts on project-owned marts (`dim_customers`, `dim_sellers`, `dim_products`, `fct_orders`, `fct_order_items`). Not on `dim_date`: its ~37 columns are generated by dbt_date.
- `data_type` uses names both engines accept (`string`, `bigint`, `integer`, `boolean`, `date`, `timestamp`, `numeric(18, 2)`); exception `double` for lat/lng → phase 3 must switch to `float64` on BigQuery (e.g. target-conditional Jinja).
- DuckDB contract check compares decimal precision/scale. Money columns in marts are cast explicitly via `to_money()` = `numeric(18, 2)` (BRL cents) instead of inheriting DECIMAL(28..38, 6) from arithmetic.
- PKs get `not_null` + `primary_key` constraints (enforced on DuckDB, informational on BigQuery) and keep `unique`/`not_null` data tests, which work on every engine.
- Generic test `is_not_before(earlier_column)`: logical invariants = error, known source defects (carrier timestamps) = warn.
- Shared column descriptions in doc blocks (`models/_docs.md`), `__overview__` replaces the default docs-site landing page.

## D18 · 2026-10-11 · Monthly-chunk ingestion and source freshness
- The Kaggle dump is static; arrival is simulated by purchase month. Order tables (`orders` + `order_items`, `order_payments`, `order_reviews` of those orders) load with `merge` on their primary keys; reference tables (customers, products, sellers, geolocation) are full snapshots, `replace`.
- Cursor = last loaded month in dlt source state (`orders_loaded_until`), committed atomically with the load. `--until YYYY-MM` caps a run; no flag loads the rest; `--full-refresh` = dlt `refresh="drop_sources"` (tables + state). Rejected: `dlt.sources.incremental` on the purchase timestamp: child tables have no timestamp and must follow their orders.
- Chunk selection runs lazily inside the resource generators, after dlt applies `refresh`; computing it in the source body would read the pre-refresh state.
- Every row gets `_loaded_at` (UTC instant of the run; TIMESTAMPTZ on DuckDB, TIMESTAMP on BigQuery): incremental cursor for dbt (phase 4) and `loaded_at_field` for freshness. Metadata column, so the "raw = all strings" rule doesn't apply.
- Freshness on all sources, `warn_after: 1 day`, no `error_after`: after the last month is loaded, order tables honestly stop changing; an error would fail every later deploy. Runs in the DuckDB CI job (fresh ingest, checks the plumbing) and in CD after ingest. Not in BigQuery PR CI (reads shared `raw`, nothing to learn).
- Migration of existing prod `raw` (replace, no `_loaded_at`) verified on a scratch BigQuery dataset: first run merges all rows without duplicates, the next is a no-op.
- `pyarrow-stubs` (dev): `pyarrow.compute` functions are generated at runtime, Pylance can't see them otherwise. Pyright: 0 errors.

## D20 · 2026-10-11 · Incremental fct_order_items
- `materialized: incremental`, `incremental_strategy: merge`, `unique_key: order_item_sk` — the one strategy both adapters support with update semantics (dbt-duckdb `merge` needs DuckDB ≥1.4).
- Cursor = `_loaded_at` from raw, carried through `stg_olist__orders` / `stg_olist__order_items`. Filter: item **or** its order loaded at/after `max(_loaded_at)` in `{{ this }}`, so an order reloaded with a new status reprocesses its items. `>=`: the last batch is re-merged (idempotent) rather than risk a gap. Customers are replaced every load, so not in the cursor. Output `_loaded_at = greatest(item, order)`.
- Rejected: `microbatch` (dbt ≥1.9). Batches by event time up to *now*; with 2016-2018 data every run would need explicit `--event-time-start/end`. A good fit later for Airflow backfills (phase 5). Evaluated for that in D65 and rejected again, with measurements.
- BigQuery: partition by `purchase_date` (month; daily would exceed partition limits for no gain at this size) + cluster by `seller_id, product_id`; config is `target.type`-conditional, DuckDB gets none.
- Contract stays enforced; `on_schema_change: append_new_columns`. `_loaded_at` type differs (TIMESTAMPTZ vs TIMESTAMP) → inline `target.type` switch.
- Unit test of the incremental branch: `overrides.macros.is_incremental: true` + fixture for `this`. The `this` fixture uses `format: sql`: a dict fixture makes dbt introspect the existing table, which fails on a fresh CI database and lacks newly added columns. Fixtures don't render macros → plain `cast(... as timestamp)`.
- Verified: DuckDB chunked run (2017-06 full → 2017-07 → rest → no-op) equals `--full-refresh` (112,650 rows, R$15,843,553.24); BigQuery full refresh + incremental run in scratch datasets, same totals.
- Prod migration: the existing prod table (plain table, no `_loaded_at`, not partitioned) can't be merged into → one-off full refresh. CD got a `workflow_dispatch` input `full_refresh` for this and future rebuilds.

## D21 · 2026-10-12 · Snapshot snap_sellers (SCD2)
- YAML-defined snapshot (dbt ≥1.9, `snapshots/snap_sellers.yml`, `relation: source(...)`): no SQL file, reads the raw source. Snapshot sources, not models, so history doesn't change when transformation logic does.
- `strategy: check` on `seller_zip_code_prefix`, `seller_city`, `seller_state`: the source has no `updated_at`. Not `check_cols: all` — `_loaded_at` / `_dlt_id` change on every load and would version every row each run.
- `hard_deletes: new_record`: a seller missing from a load gets a closing version with `dbt_is_deleted = 'True'`; reappearing opens a new one.
- Schema `snapshots` (`ci_pr_*_snapshots` in CI); `drop_ci_datasets` got the `_snapshots` suffix (would have leaked CI datasets).
- Tests: `dbt_scd_id` unique/not_null, (`seller_id`, `dbt_valid_from`) unique, `seller_id` unique where `dbt_valid_to is null` (one open version).
- The dump never changes sellers → prod has one version per seller. Mechanics shown by a local demo in the README (change + delete + restore → 3 versions each). `dim_sellers` stays current-state; nothing reads the snapshot yet.
- Verified: DuckDB demo; BigQuery scratch dataset (build + re-snapshot = no new versions, cleanup drops `_snapshots`).

## D23 · 2026-10-12 · Airflow in CI, BigQuery DAG cleanup
- CI job `airflow DAGs parse` (PRs only): builds the image (buildx, GHA cache), runs `airflow/check_dags.py` in it — `DagBag` over the DAG folder, fails on import errors, a missing DAG or a DAG without dbt tasks. No metadata DB, no warehouse; a dummy `{}` key renders the BigQuery DAG (parsing never authenticates). Cosmos cache off (it lives in Airflow Variables = DB).
- `LoadMode.DBT_MANIFEST` instead of `DBT_LS`. Found on the first BigQuery run: Airflow 3 re-parses the DAG file in every task, and Cosmos' `dbt ls` cache lives in Airflow Variables, which tasks can't write → every task ran two uncached `dbt ls` (one per DAG in the file). With 10 parallel tasks on 4 CPUs that took >3 min, past the import timeout → endless retries; the DuckDB DAG hid it (1-slot pool, ~15 s). Now `dbt parse --target-path target_airflow` in `airflow-init` (and CI) writes the manifest; parse is 0.1–3 s (cold ~20 s). Cost: rerun `airflow-init` after changing models (execution always uses the live project; only the graph comes from the manifest). Import-timeout overrides (tried first: 180 s) removed.
- `drop_ci_datasets` → `drop_isolated_datasets`, allowed on targets `ci` and `airflow`, also drops `<schema>_raw` and `<schema>_raw_staging` (dlt dataset of the Airflow DAG and its merge staging; the first real run left `airflow_raw_staging` behind). Still refuses dev/prod.
- Pyright/Pylance: `airflow/` is an execution environment with `reportMissingImports` and `reportUnusedExpression` off. Airflow/Cosmos are only in the image (separate on purpose, D22); the parse job is that code's check.
- Task logs in the UI: `[api] secret_key` shared across components (local value, like the JWT secret) + a shared `airflow-logs` volume. Unset, each component picked a random key and the api-server's signed request to the scheduler's log server (LocalExecutor) was rejected.
- Verified on BigQuery: backfill 2016-09..10 → same numbers as DuckDB (raw/`fct_orders` 4 + 324, `fct_order_items` 369 over 2 loads, 1 snapshot version per seller), prod untouched; then `drop_isolated_datasets --target airflow` left only prod datasets.

## D25 · 2026-10-12 · Cosmos watcher mode (Airflow speed-up)
- `ExecutionMode.WATCHER` for both DAGs (revisits D22). A producer task runs `dbt source freshness` + one `dbt build`; every node is a deferrable sensor reading the producer's per-node results (XCom from dbt's JSON log). Measured, empty warehouse, months 2016-09 / 2016-10: DuckDB 29.1 / 28.0 → 5.6 / 5.7 min; BigQuery 18.9 → 8.9 / 6.1 min (first run without a Cosmos partial-parse cache). Same data as before on both (raw/`fct_orders` 328, `fct_order_items` 369 over 2 loads, 1 snapshot version per seller), prod untouched.
- Why it was slow: LOCAL mode ran one dbt process per node, each paying Python/dbt start + project parse (~36 s per task); on DuckDB one at a time (1-slot pool), on BigQuery 10 at a time on 4 CPUs (each task minutes). Tasks also started from the host's `partial_parse.msgpack` (Windows, other profile) → full reparse. Watcher pays that once per run, and dbt threads give DuckDB parallelism inside its single writer process.
- DuckDB pool only on the writers: `dlt_ingest` + producer (`ExecutionConfig.setup_operator_args`). Sensors in the 1-slot pool would wait for the producer they watch. CI `check_dags.py` asserts the pool holds exactly these two (mutation-checked).
- Watcher constraints found by running it: no `TestBehavior.BUILD` (→ `AFTER_EACH`, a run + test sensor per model, 53 tasks); detached multi-parent tests fail ("no information about the node": the producer reports tests per model) → `should_detach_multiple_parents_tests=False`; the default freshness callback skips nodes below stale (warn) sources → `no_freshness_skips` (freshness is warn-only, D18; a month without orders is honestly stale); unit tests excluded from the producer (`--exclude-resource-type unit_test`, CI's job).
- Re-runs: the producer skips itself on attempt 2+, and sensors then run their own node's dbt command — on DuckDB outside the pool → file-lock failures (found via a backfill `--reprocess-behavior`, which reuses run ids). Hence `retries=0` and "re-run = new DAG run, not Clear" (airflow/README.md). Data is safe either way (DuckDB lock; models idempotent). Verified: a new run for the already loaded 2016-10 → success, 53/53 tasks, data unchanged. Rejected: pool on the sensors (52 sensors serialized after the producer, ~7 min) to protect a path we don't use.
- BigQuery is still slower than DuckDB here: ~1 s of job overhead per node × 128 nodes on tiny data, slower dlt load jobs. Left for later: freshness + build are two dbt invocations in the producer (~40–60 s of start + parse each run); seeding a per-target partial parse.

## D28 · 2026-10-13 · Live feed: hourly replay of the dump, alerts, dashboard on Airflow marts
Question: the DAGs ran, but what happens when new data arrives? Olist never gets new data, so the feed is simulated. Three PRs (choices made in brackets).
- **Replay (PR 7.1, hourly):** DAGs `@hourly`, `start_date` 2026-10-13, no `end_date`, `catchup=False`. Each run loads the next purchase month *that has orders* (`pipeline.py --next`, cursor in dlt state). Not the next calendar month: 2016-11 has no orders, and an empty chunk never moves the cursor (stuck forever). ~25 runs replay 2016-09..2018-10, then each run loads 0 orders.
- Replaces the monthly schedule over 2016-09..2018-10 + backfill (D22): its `end_date` was in the past, so the scheduler never started a run by itself; the run's data interval no longer means a dump month. Manual `until` param stays for catch-up / recovery.
- `has_new_orders` (ShortCircuitOperator) skips the dbt group when the ingest's last stdout line (its XCom) is `orders_loaded=0`: no rebuild for no data, no BigQuery cost every hour once the dump is used up. Runs with `until` / `full_refresh` always build: re-running a month whose dbt failed loads 0 new orders but must rebuild. Mid-feed a failed dbt step heals on the next run (incremental cursor is still behind the rows).

- What was built for the test: both facts with `event_time='purchased_at'`, `batch_size='month'`, `begin='2016-09-01'`, `lookback=0`, month partitions on `purchase_date` on BigQuery (its microbatch is `insert_overwrite` and needs `partition_by` with the batch's granularity; DuckDB runs delete + insert per batch); `event_time` on `int_orders_joined_to_customers`, so dbt filters the orders input to each batch's month. The per-order aggregates (items, payments, delivery, reviews) have no purchase time and are read whole per batch. Windows came from `DBT_EVENT_TIME_START` / `_END` (the env form of `--event-time-start/--event-time-end`; an empty value counts as not set), planned per caller: CI/CD the whole dump, Airflow's hourly run the months the load brought, a manual backfill DAG its params.
- The window is not optional. Without one a microbatch run ends at the wall clock: a first build runs 122 monthly batches (2016-09 to 2026-10, mostly empty; DuckDB 15.4 s for `fct_order_items`, 64.8 s for `fct_orders`), and every later run builds only the current month, so the dump's months are never picked up again. Every dbt call that builds the facts would have to pass it.
- Correctness held: with the window both facts equal the current models (DuckDB: `except all` both ways, 0 rows; BigQuery: row count + `bit_xor(farm_fingerprint(to_json_string(row)))` per table, including `fct_orders_v1`). A one-month backfill rebuilt only that month: with 2017-11 zeroed and a week of 2018-03 deleted, a run with the 2017-11 window restored 2017-11 and left 2018-03 as it was (the relationships and row-count tests failed on it, as they should); after a second run for 2018-03 the fingerprints matched a full build of the current models.
- DuckDB (full dump, 99,441 orders, 112,650 lines): `fct_order_items` full build 2.5 s as a table vs 4.3 s in 26 batches, `fct_orders` 2.1 s vs 15.7 s; one month 1.0 s and 2.0 s, i.e. no faster than a full rebuild. Whole `dbt build --full-refresh` 24.5 s → 39.8 s.
- BigQuery, from `INFORMATION_SCHEMA.JOBS_BY_USER`:

  | | current models | microbatch |
  |---|---|---|
  | `fct_orders`, full build | 3 jobs, 50 MiB | 103 jobs, 2,020 MiB |
  | `fct_order_items`, full build | 3 jobs, 33 MiB | 103 jobs, 1,548 MiB |
  | whole `dbt build` | 250 jobs, 2,420 MiB, 107 s | 603 jobs, 7,505 MiB, 156 s |
  | one month, both facts | (full rebuild: 6 jobs, 83 MiB) | 8 jobs, 143 MiB |

- Why it costs more: the batch filter sits on views over raw tables that are not partitioned, and BigQuery bills the full columns a query reads (at least 10 MB per table), however few rows the filter keeps. Each batch reads the same raw columns again, plus the target partition it replaces (about 4 jobs per batch). So a single month costs more than rebuilding everything, and a full build costs about 40 times the bytes. A CD deploy rebuilding the whole dump would add about 5 GB; passing only the loaded months would need the deploy to skip the facts when nothing was loaded and nothing changed, and still pay the 26-batch rebuild whenever their SQL changes.
- Other costs found: switching the existing prod table needs a one-off full refresh (microbatch into the unpartitioned `fct_orders` ran its batches concurrently and 3 of 26 failed with `Could not serialize access to table ... due to concurrent update`); and `lookback=0` would drop what the merge cursor does today, reprocessing items whose order row was reloaded with a new status.
- When to look again: when raw (or a layer below the facts) is partitioned by purchase time, so a batch reads only its month, and the data is large enough that a full rebuild hurts. Until then the dump is 100k orders and a full rebuild of the facts costs 83 MiB on BigQuery and about 5 s on DuckDB. Partitioned raw was evaluated in D69: at this size it bills the same bytes.

## D68 · 2026-10-24 · Elementary recomputes the whole training window for incremental models
- Issue #119: `freshness_anomalies` on `fct_orders` warned (4 days) in one full build and passed in the next on the same data and clock. The two builds were not the same project: the passing one ran during the D65 evaluation, with `fct_orders` materialized as microbatch (incremental). With the table model it warns in every build (dev history since D38, three more `--full-refresh` builds, prod).
- Cause, in Elementary 0.26: for a table, every anomaly test recomputes all buckets of the training window and scores them. For an incremental model (sources count too) it computes only buckets that have no stored metric yet plus the detection period, and scores them together with the stored history, but only history written after the model's last full refresh (`dbt_run_results.full_refresh`). The stored buckets older than that are neither recomputed nor scored, so after a second `--full-refresh` the training set is the detection period alone: 2–5 points per weekday instead of 14. In the passing build the expected gap became 128.7 h instead of 44.6 h, and the 173–245 h gaps of 2018-10-10 to 10-13 scored below the threshold.
- The same applies today to `volume_anomalies` on `fct_order_items` (merge on `_loaded_at`, D20): after two `--full-refresh` builds on DuckDB it scored 23 buckets with 2–5 training points. It still passed, but it could not flag anything. Prod is not affected yet: no full refresh since Elementary was added, so its history is unfiltered (14 training points in every deploy). A CD run with the `full_refresh` input or an Airflow run with `full_refresh` would put it in the same state, and with the fixed clock of the dump the old buckets would never be recomputed.
- Var `force_metrics_backfill: true` (`dbt_project.yml`) makes Elementary recompute the whole training window on every run, for incremental models as for tables. Verified on a copy of the dev DuckDB file in that state: two `--full-refresh` builds and a normal build, each scoring 91 buckets with 14 training points; `freshness_anomalies` warns 4 in each. Test time unchanged (3.7–4.6 s vs 3.4–6.2 s). On BigQuery the bytes billed should not change (not measured separately): the bucket filter is on `purchased_at`, not the partition column, so each test reads the same columns either way.
- Rejected: `exclude_detection_period_from_training` or other tuning of the freshness test, which would hide the cause; dropping old metrics after a full refresh (a delete in Elementary's tables, outside dbt).

## D69 · 2026-10-25 · Partitioning the raw order tables on BigQuery, measured
- Question (#116, after D65): would partitioning the raw order tables make the backfill path (one purchase month) or the incremental path (rows loaded since the last run) cheaper on BigQuery? Result: at this size no layout bills fewer bytes on any path, and the incremental model had to be rewritten before any partition could be pruned. Partitions by purchase month are rejected. Partitions by `_loaded_at` and the rewritten incremental filter were built anyway, as a demonstration of the incremental path that pays off once the data grows (D70).
- Evaluated on copies of prod `raw` in throwaway datasets (`ci_part_check_*`, as `olist-ci`, dropped afterwards), three layouts: as today; partitioned by a `_purchase_month` DATE (month granularity) on all four order tables, the child rows taking their order's month; partitioned by `_loaded_at` (hour granularity). `_loaded_at` was rewritten to simulate the replay: one load per purchase month, an hour apart. Queries ran without cache; bytes are `total_bytes_billed` of each job. The read of a `fct_orders` build (orders, items, payments and reviews aggregated per order, customers) and the read of the `fct_order_items` incremental query (cursor at the 2018-08 load, 7,249 rows) were run against each layout, and again on a 10× copy (order and customer ids suffixed per copy, same months and load times).

  | | today | `_purchase_month` partitions | `_loaded_at` partitions |
  |---|---|---|---|
  | full read | 50 MiB | 50 MiB | 50 MiB |
  | one month (2017-11, 7,544 orders) | 50 MiB | 50 MiB (9.3 MiB processed) | 50 MiB |
  | incremental, as in the model (`or`, cursor from a subquery on `{{ this }}`) | 40 MiB | 40 MiB | 40 MiB |
  | incremental, cursor as a literal, `and` on both tables | 31 MiB | 31 MiB | 30 MiB (8.0 MiB processed) |
  | 10×: one month | 346 MiB | 97 MiB | 346 MiB |
  | 10×: incremental as in the model | 312 MiB | 312 MiB | 312 MiB |
  | 10×: incremental, literal cursor, `and` | 312 MiB | 312 MiB | 83 MiB |

- Why nothing changes today: BigQuery bills at least 10 MiB for every table a query reads. The raw order tables are 7–18 MiB each, so a pruned month (9.3 MiB processed for five tables) is billed the same 50 MiB as the whole dump. Partitions pay off only once a table's read columns are several times that floor; at 10× the data a one-month read drops to 97 MiB, most of it the unpartitioned customers snapshot.
- Why the incremental path needs more than partitions: the cursor in `fct_order_items` is `max(_loaded_at)` from a subquery on `{{ this }}`, and BigQuery prunes partitions only on constant filters, so the query reads the whole table in every layout, also at 10×. The `or` across items and orders (an item is reprocessed when its order is reloaded) cannot prune either side. Pruning needs the cursor computed first (`run_query` → literal) and a filter per table, which changes what the model reprocesses.
- What that rewrite involves (built in D70): the cursor read by a query of its own before the model's (not in unit tests, whose `this` is a fixture, not a table), and the `or` replaced by a `union` of items loaded since the cursor and all items of orders loaded since it. A plain `and` is equivalent only while an order and its child rows always load in the same chunk, true for the replay, not for a live source where a status update reloads only the order row. Today it would not pay: the cursor query bills the 10 MiB floor itself (31 + 10 MiB against 40 MiB). Other limits found: BigQuery allows 4,000 partitions per table, so hour partitions on `_loaded_at` last about 166 days, while day partitions put most of the hourly replay into one partition; the merge still scans the whole target, and `incremental_predicates` on `purchase_date` would duplicate rows whose purchase date falls outside the window.
- Microbatch (D65) stays rejected: its batches pay the same per-table floor in every job, and one month (143 MiB) would still cost more than a full rebuild of the facts (83 MiB).
- Purchase-month partitions would also need a typed partition column in raw (`_purchase_month`, a metadata column like `_loaded_at`, D18, added by the pipeline to every child row) and help only backfills, which stay full rebuilds (D65). Partitions on `_loaded_at` need no new column.
- When to look again at purchase-month partitions: when a raw order table's read columns reach about 100 MiB (roughly 10× the dump) and backfills by month are needed.

## D84 · 2026-10-30 · Cohort retention and LTV mart, a dashboard page over it
- Until now retention was one number, `repeat_customer_rate` by first order (D35). `fct_customer_cohorts` adds when people come back and what a cohort is worth: one row per acquisition cohort (month of the first order) and month since it, group `parties`, public with an enforced contract, surrogate key over the two grain columns (as `fct_order_items`).
- Same rules as the existing marts, so the numbers reconcile instead of competing: cohort = month of `dim_customers.first_order_at` (all statuses); active = any order that month (as `orders_count`); revenue = `paid_amount` of orders not canceled/unavailable (as `lifetime_value`). On the full dump: cohort sizes sum to the 96,096 people of `dim_customers`, orders to the 99,441 of `fct_orders`, final cumulative revenue to R$ 15,739,137.01 = sum of `lifetime_value`; month-0 retention is 1 for every cohort (also an output-contract SQL rule).
- A spine of calendar months (`dim_date`) from each cohort to the latest month with orders: months nobody came back in are rows with zeros, so curves and the heatmap have no holes and cumulative values carry on; months after the data get no rows, so a young cohort simply has fewer months. Table materialization: 327 rows, rebuilt in seconds (10 MiB billed on BigQuery); an incremental model would add state for nothing.
- `retention_rate` is integer / integer: a float on all three engines. `cast(... as dbt.type_float())` gives a 4-byte FLOAT on DuckDB, which fails the contract's DOUBLE.
- Semantic layer: semantic model `customer_cohorts` (time axis = cohort month), metrics `cohort_size`, `retained_customers`, `cohort_retention_rate` (ratio; meaningful grouped by `cohort__months_since_first_order`), `cohort_revenue_to_date`, `ltv_3_months` (revenue per acquired person in calendar months 0-2; both sides filtered to month 2, so cohorts younger than that drop out of numerator and denominator alike). Saved query `cohort_retention_curve`. Calendar months, not 90 days: the mart's grain is the month.
- Dashboard page "Cohorts & retention" (a page of its own: the smoke test expects four tiles per page): new customers, back in month 1 and 3, 3-month value per customer; heatmap of the share that ordered again (months 1-12, month 0 left out so the scale shows the returns), retention curve and value-per-customer curve, a table view. Cohorts whose month overlaps the picked period. Tiles are checked against `mf query` like the other pages (D35); the usage agreement lists the new table, columns and metrics.
- Output contract `olist-marts` and the product 1.0.2 → 1.1.0: a new table is not breaking, the dashboard agreement (major 1) stays valid.
- Findings on the data: 0.48 % of new customers order again in the month after their first, 0.23 % in month 3; the 3-month value per acquired person is R$ 162 and grows only to ~R$ 170 by month 12. Olist is close to a one-purchase marketplace; acquisition, not retention, drives revenue.
- Verified: DuckDB (copy of the full dump) and BigQuery (`--defer` to prod, scratch `ci_cohort_check_*`, dropped) row by row, 327 rows, 0 differing values; Databricks (catalog `olist`) the same checksums; output contract 40 new checks pass on DuckDB.

## D86 · 2026-10-31 · One `week_of_year` on every engine
- `dim_date.week_of_year` and `prior_year_week_of_year` come from `dbt_date.week_of_year`, which the package dispatches per adapter with different meanings: `ceil(day_of_year / 7)` on DuckDB, `date_part('week')` (ISO-like) on Snowflake and Databricks, `EXTRACT(WEEK)` on BigQuery. Found by the Snowflake vs DuckDB mart diff (D85, #187); no model, metric or dashboard page reads the columns yet.
- The project overrides the macro through `dispatch` (`macro_namespace: dbt_date`, search order `olist` first) with one `default__week_of_year` for every engine: `floor((day_of_year + 7 - day_of_week) / 7)`, `day_of_week` with Sunday = 1 (dbt_date's non-ISO variant, equal across engines). It reproduces BigQuery's `EXTRACT(WEEK)`: weeks start on Sunday, days before the year's first Sunday are week 0 (as `strftime %U`). BigQuery prod was the reference because it is what consumers already read; ISO weeks stay in `iso_week_of_year`. Rejected: dropping the two columns (a breaking change to a public mart for no gain once they agree) and one override per adapter (four definitions to keep equal instead of one).
- dbt's dispatch looks for `<adapter>__` then `default__` in each package of the search order before moving to the next package, so the project's `default__` wins over the package's `duckdb__week_of_year` as well.
- Singular test `assert_dim_date_week_of_year`: seven hand-checked days (years starting on Saturday, Sunday and Monday, the last day of the dimension).
- Verified: BigQuery scratch build vs prod `marts.dim_date` 0 differing rows both ways (prod data unchanged by the deploy); DuckDB, Snowflake and Databricks builds equal it on all 1,460 rows. Before the fix 887 DuckDB rows and 1,096 Snowflake rows differed from it.
